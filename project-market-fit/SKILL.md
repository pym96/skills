# Project-Market Fit

Treat fit as a hypothesis about which hiring problems existing work helps solve. Test that hypothesis before investing in project changes. This is project-to-role relevance, not proof of commercial product-market fit.

## 1. Establish the target

Extract the target, available projects, and time constraints from context. Use a role family's shared needs for durable investment and a specific team's needs for tailoring. One JD is enough to start, but does not establish a market-wide pattern. If no target is inferable, ask for the role family or vacancy before tailoring.

**Done when:** The target and available project material are identified; missing requirements remain explicit unknowns.

## 2. Mine existing contributions

Load `engineering-judgment` and its project reference for technical analysis. Load `grilling` when unresolved questions require dialogue; follow its one-question-at-a-time process, recommending a direction and waiting for the answer. Inspect available artifacts before asking what they can answer; do not re-interview facts already established. Locate missing dependencies in installed skills; if unavailable, report the limitation and request missing project facts one at a time without inventing them.

Create one **fit map** and update it throughout the run:

| Role task and intended outcome | Demand basis and status | Existing contribution | Result or gap | Next decision |
| --- | --- | --- | --- | --- |

For demand status, distinguish explicit requirement, inference, and hypothesis. Attach source links and dates where available; distinguish reported interview observations from interpretations. Map transferable contributions without rewriting their original motivation to pretend they were built for this employer.

**Done when:** Each contribution selected for positioning has a map entry, or the map identifies why no credible connection is yet available. Establish the existing work before proposing additions.

## 3. Route and resolve the gap

| Gap | Action |
| --- | --- |
| Relevant contribution is buried in a feature list | Use engineering-judgment to improve the explanation. |
| The team's task or bottleneck is unclear | Read [research.md](references/research.md), conduct the research, then update the map. |
| Relevant implementation lacks evidence of benefit | Read [improvement.md](references/improvement.md) and define a bounded validation task. |
| A supported role need is not covered | Read [improvement.md](references/improvement.md) and define the minimum project change. |
| Adaptation is weakly relevant or too costly | Compare another project or a smaller standalone experiment; surface any proposed role change for the user to decide. |

Resolve decision-changing upstream uncertainty first. Research findings may change the gap classification; route again only when they do. Sparse resume text alone does not justify building. Require a concrete role task, a supported problem, and an acceptance method for substantial investment; otherwise limit the recommendation to low-cost exploration.

**Done when:** Each material gap has a supported disposition. Any necessary research has been performed or a specific access/input limit reported—not merely placed on a future to-do list. Validation and implementation remain proposals unless their execution is authorized.

## 4. Deliver the current position and next investment

Use engineering-judgment's resume reference to produce copy-ready bullets and a brief project explanation. Keep uncertainty and source notes in the fit map, rather than weakening every sentence with caveats. If no credible fit exists, explain the mismatch instead of manufacturing a bullet.

Return the positioning, fit map, and the smallest prioritized next tasks defined by the selected branch. Match the user's requested scope; do not force all artifacts into a narrow follow-up. "No project change needed" is a complete outcome.

**Done when:** Current accomplishments are separated from proposed benefits; the next action is bounded and names what result would change the recommendation.

## 5. Close the loop when feedback arrives

Default to recommendations. Execute project changes or experiments when the user's request authorizes them, without asking again for existing authorization. Read [improvement.md](references/improvement.md) before execution or evaluating its results. Update the affected fit-map entries and positioning from observed outcomes; negative results can justify stopping, simplifying, or switching projects.

For research or interview feedback, revisit only affected demand hypotheses and route through step 3. An interviewer's preference, rejection, or acceptance does not by itself establish market fit.

**Done when:** Each new observation has an explicit effect on the recommendation, or a stated reason for leaving it unchanged. Authorized execution includes validation and narrative updates, or a concrete blocker and remaining work.
